# D-04 — Self-knowledge cohort (design)

**Status:** Design (no implementation)
**Date:** 2026-04-18
**Parent:** [Model X spec, Section 11 — phased delivery](./2026-04-16-model-x-autonomic-design.md)
**Delivers:** `knowledge/self/` infrastructure + `FIRE_CAPABILITY_SCAN` + `FIRE_SELF_STUDY`.

---

## 0. Context

D-01, D-02, D-03 are merged. The autonomic scheduler now fires 7 levers (4 immune, 3 autonomic) with per-rule cooldowns on a single-tempo 30s tick. D-04 adds the first self-knowledge levers — the ones that build the agent's map of its own code, tools, and environment.

**Scope split note:** Section 11 of the parent spec originally bundled four levers into D-04 (`FIRE_SELF_STUDY`, `FIRE_CAPABILITY_SCAN`, `FIRE_NOTE_CURATION`, `FIRE_GRAPH_MAINTENANCE`) plus `backend/background.py` retirement. During brainstorming on 2026-04-18 we split that into two cohorts that write to different parts of `knowledge/`:

- **D-04 (this spec)** — Self-knowledge: `CAPABILITY_SCAN` + `SELF_STUDY` + `knowledge/self/`.
- **D-05** — Knowledge curation: `NOTE_CURATION` + `GRAPH_MAINTENANCE` + `background.py` retirement.

The full Model X vision (19-lever catalog, Section 3 of parent) is unchanged. Only the order of delivery is restaged.

**Goal:** give the agent two read-only-ish levers that observe its own codebase and environment, and persist that observation as markdown under `knowledge/self/`. Future levers (hybrid-searcher integration, L2 diagnosis) will retrieve from this store.

**Non-goals:** `bge-m3` embedding indexing of the new notes (D-05/D-06), hybrid-searcher integration, auto-update of `architecture_overview.md`, OS-level Linux inventory (`dpkg`, `systemctl`, `ollama list`) — deferred to deployment-time D-07 body cohort.

## 1. `knowledge/self/` structure

```
knowledge/self/
├── modules/                # FIRE_SELF_STUDY: one note per backend/**/*.py
├── tools/                  # FIRE_CAPABILITY_SCAN: one note per backend/tools/*.py
├── skills/                 # FIRE_CAPABILITY_SCAN: one note per backend/skills/<name>/
├── mcp_servers/            # FIRE_CAPABILITY_SCAN: channels.json summary
├── server_inventory.md     # FIRE_CAPABILITY_SCAN: psutil snapshot (idempotent rewrite)
└── .gitkeep
```

**Conventions (all four cohorts share):**

- File names are slugified: `backend/autonomic/layer0.py` → `knowledge/self/modules/autonomic__layer0.md` (double-underscore for path separator, keeps names filesystem-safe).
- Each note has a YAML frontmatter: `module`, `category: self`, `updated`, plus cohort-specific fields (`source_mtime`, `loc` for modules; `entry_point` for tools; etc.).
- Notes are overwritten idempotently on each tick — no append history. Historical versions live in git.

`architecture_overview.md` is NOT generated by either lever in D-04. It stays as a hand-maintained anchor file if the user wants one; otherwise absent.

## 2. `FIRE_CAPABILITY_SCAN`

**Category:** autonomic. **Safety:** green. **Executor:** python (no cortex call). **Cadence:** every 6h (cooldown=21600s).

**Purpose:** inventory the agent's own tools, skills, MCP channels, and host environment into `knowledge/self/`. Pure filesystem walk + psutil; no LLM, no network.

**Behavior (`run`):**

1. **Tools** — for each `backend/tools/*.py` (excluding `__init__.py`):
   - Read the file, extract the module docstring (first top-level triple-quoted string).
   - Instantiate `backend.tool_registry.get_registry()` and collect any `Tool` entries whose source file matches.
   - Write `knowledge/self/tools/<slug>.md` with frontmatter `{module, category: self, kind: tool, updated, loc, source_mtime}` and body sections `## Purpose` (from docstring) + `## Registered tools` (from registry).

2. **Skills** — for each `backend/skills/<name>/` subdirectory:
   - Read `SKILL.md` if present; else build a fallback from directory listing.
   - Write `knowledge/self/skills/<name>.md` with frontmatter `{skill, category: self, kind: skill, updated, file_count}` and body `## Description` + `## Files` listing.

3. **MCP / channels** — read `knowledge/channels.json`:
   - Write `knowledge/self/mcp_servers/channels.md` with one-line per channel: `| id | type | enabled | auto_start | status |` markdown table.

4. **Server inventory** — via `psutil`:
   - `platform.platform()`, `platform.python_version()`, `platform.machine()`.
   - `psutil.cpu_count(logical=False)` / `logical=True`, `psutil.virtual_memory()`, `psutil.disk_usage(knowledge_root)`, `psutil.boot_time()`.
   - Write `knowledge/self/server_inventory.md` with `{category: self, updated, host}` frontmatter and a plain-prose body plus a key-value table.

5. Return `LeverReport` with `outcome = {tools_written, skills_written, mcp_written, server_written: bool}` and `reason = f"scanned:{total}_artifacts"`.

**Preconditions:** always True. All I/O is local filesystem + psutil, no external dependencies.

**Error handling:** each of the four sub-steps is wrapped in try/except; a failure in one step does not block the others. Per-step outcome fields indicate success (True/int>0) or failure (False/0). Final status is `SUCCESS` unless all four sub-steps failed.

## 3. `FIRE_SELF_STUDY`

**Category:** autonomic. **Safety:** green. **Executor:** claude (delegates to cortex). **Cadence:** daily (cooldown=86400s).

**Purpose:** generate and refresh markdown notes that describe each `backend/*.py` module — purpose, public interface, dependencies — so L2/L3 layers can retrieve them via hybrid search.

**Throttling:** at most **`max_modules = 3`** modules per tick. With ~36 backend modules, full pass across the codebase takes ~12 days; when a file is modified, it is prioritized and re-processed on the next daily tick.

**Priority order per tick:**

1. Modules with no existing note in `knowledge/self/modules/` (new files).
2. Notes where frontmatter `source_mtime < file.stat().st_mtime` (stale — source changed since last study).
3. Oldest notes by frontmatter `updated` (periodic refresh).

**Behavior (`run`):**

1. Walk `backend/**/*.py` (skip `__pycache__`, `*/tests/*`, `*/.venv/*`). Build candidate list.
2. For each candidate, compute priority bucket (new / stale / old). Sort buckets; take the first `max_modules`.
3. For each target:
   1. Read the source file. If line count > 3000, truncate to first 3000 lines and append `\n# [truncated]`.
   2. Call `router().call_json(TaskType.TASK_ANALYSIS, SELF_STUDY_SYSTEM, source_text, max_tokens=1500, temperature=0.2)`.
   3. Expect JSON `{purpose, public_interface, dependencies, notes}` (schema in Section 3.1 below).
   4. Write `knowledge/self/modules/<slug>.md` with YAML frontmatter + four markdown sections.
4. Return `LeverReport` with `outcome = {modules_processed, modules_skipped, modules_total}`, `reason = f"studied_{processed}_modules"`, and `follow_ups = []`.

**Preconditions:** always True. Cadence is enforced by the rule's cooldown.

**Cost cap note:** 3 modules × one cortex call each × ~1500 output tokens ≈ 4500 tokens output per daily tick. On Claude Sonnet pricing, that's roughly a few cents per day — acceptable.

**Error handling:** per-module try/except around the cortex call and file write. A failure on one module increments `modules_skipped` but does not abort the tick.

### 3.1 Prompt contract — `SELF_STUDY_SYSTEM`

```
You are the self-knowledge module of an AI agent. You read one Python module
from the agent's own source tree and produce a short structured description.

Return strictly JSON:
{
  "purpose": "one-paragraph summary of what this module is for",
  "public_interface": [
    {"name": "<class or function name>", "kind": "class|function|constant", "one_line": "<short description>"}
  ],
  "dependencies": ["<internal module>", ...],
  "notes": "optional observations about complexity, invariants, gotchas — 2-3 sentences"
}

Rules:
- Skip __dunder__ helpers unless they define the public API.
- "dependencies" lists imports from the same project (backend.*), not stdlib or third-party.
- Max 12 entries in public_interface.
- No speculation about what the module might do — describe what it does.
```

## 4. Layer 0 rule extension (7 → 9)

`backend/autonomic/layer0.py::default_rules()` grows from 7 rules (post-D-03) to 9. The first 4 reactive rules and the 3 D-03 scheduled rules are unchanged. Appended:

```python
LayerZeroRule(
    name="capability_scan_tick",
    predicate=lambda s: True,
    lever="FIRE_CAPABILITY_SCAN",
    params={},
    cooldown_seconds=21600.0,  # 6h
),
LayerZeroRule(
    name="self_study_tick",
    predicate=lambda s: True,
    lever="FIRE_SELF_STUDY",
    params={},
    cooldown_seconds=86400.0,  # daily
),
```

**Ordering rationale:** both new rules are `predicate=True` schedule-driven. Placed at the end means reactive rules and the D-03 scheduled rules (integrity, goal_propose, consolidation) still preempt them. Between themselves, `capability_scan_tick` comes before `self_study_tick` so a fresh inventory lands before a tick where `SELF_STUDY` reads files (not a hard dependency — both read the filesystem directly — but it preserves a "scan, then study" mental model).

`backend/autonomic/levers/__init__.py::register_default_autonomic_levers()` grows from 3 to 5 registrations. No new function — extend the existing one.

## 6. Testing strategy

**Unit tests — `tests/autonomic/test_self_knowledge_levers.py`:**

- **`FIRE_CAPABILITY_SCAN`** (7 tests):
  - metadata (name, category, safety, executor).
  - tools subpass — creates `<knowledge_self>/tools/*.md` for each `backend/tools/*.py`.
  - skills subpass — creates `<knowledge_self>/skills/<name>.md` for each skill dir.
  - channels subpass — reads a seed `channels.json`, writes `mcp_servers/channels.md`.
  - server_inventory subpass — psutil values appear in the output file.
  - partial-failure isolation — mock one subpass to raise; verify others still ran.
  - outcome counts match filesystem state.

- **`FIRE_SELF_STUDY`** (7 tests):
  - metadata.
  - priority picks new modules first when no notes exist.
  - priority picks stale modules (`source_mtime` frontmatter < actual file mtime) second.
  - priority picks oldest `updated` last.
  - caps at `max_modules = 3` per tick.
  - skips `__pycache__`, tests, `.venv`.
  - truncates files > 3000 lines before sending to cortex.
  - one module per call to `router().call_json` (not batched).
  - cortex failure on one module doesn't abort other modules.

**Integration test — `tests/autonomic/test_d04_integration.py`** (3 tests, synchronous tick calls like D-03):

- two consecutive ticks fire `FIRE_CAPABILITY_SCAN` then `FIRE_SELF_STUDY` (cooldown fall-through).
- `knowledge/self/modules/` contains at least one note after SELF_STUDY runs.
- reactive rule (`errors_present`) still preempts both new scheduled rules when an error is seeded.

**Mock strategy for cortex:**

- `patch("backend.autonomic.levers.self_study.router")` — replace `router()` with a Mock whose `call_json()` returns canned JSON.
- Inject tmp paths via `params` overrides (pattern established in D-03 integration tests).

**Test count target:** ~17 new tests. Combined autonomic suite post-D-04: ~156 tests.

## 7. Open questions (not blocking)

1. **Slug separator for module path** — `backend/autonomic/layer0.py` → `autonomic__layer0.md` vs `autonomic_layer0.md` vs `autonomic-layer0.md`. Recommend `__` (double underscore) to avoid colliding with real module names that contain single underscores. Resolve in plan.
2. **Tool/skill note updates on no-change** — rewrite every 6h even when nothing changed? Simpler: yes (idempotent). More efficient: compute hash of source, skip write on unchanged. Recommend simple: always rewrite. Revisit if disk I/O becomes an issue.
3. **`source_mtime` format** — ISO 8601 string vs Unix float. Recommend ISO 8601 (consistent with other frontmatter timestamps in the project). Resolve in plan.
4. **Large files** — any current `backend/*.py` > 3000 lines? `main.py` is 1680, `llm.py` is 1267, `agent.py` is 1152 — all under the limit. So truncation is a defensive safeguard, not a current necessity. Leave the safeguard in; no action needed.
